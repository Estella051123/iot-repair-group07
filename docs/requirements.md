# 需求说明

本文件对应实验一 FR-01 至 FR-03，只描述功能，不描述界面实现。
本次实验不实现网页、数据库、账号系统和真实物联网通信，设备数据使用 `data/devices.csv` 中的模拟清单。

## 1 范围与角色

系统只处理"查看设备—提交报修—更新工单状态"这一条主流程。

| 角色 | 职责 | 可以使用哪些功能 |
| --- | --- | --- |
| 报修人 | 发现设备故障，查看设备信息并提交故障描述 | FR-01 查看设备信息、FR-02 提交报修 |
| 维修人员（维护人员） | 接单维修，推进工单状态直至完成 | FR-01 查看设备信息、FR-03 更新工单状态 |

说明两条边界：

- 数据库、传感器设备本身、GitHub 都不是操作者，不画成参与者。
- 报修人不能更新工单状态，维修人员不能代替报修人提交报修。

### 1.1 状态取值

工单状态在程序中只使用三个固定英文值，中文只用于显示。

| 中文状态 | 程序中的固定值 | 含义 |
| --- | --- | --- |
| 待处理 | `PENDING` | 工单刚创建，尚未开始维修，是唯一初始状态 |
| 处理中 | `PROCESSING` | 维修人员已开始维修 |
| 已完成 | `COMPLETED` | 维修结束，本次业务终态，不再流转 |

### 1.2 模拟设备清单（`data/devices.csv`）

| deviceId | name | location |
| --- | --- | --- |
| DEV-001 | 温湿度传感器 | A101教室 |
| DEV-002 | 智能门锁 | B202实验室 |
| DEV-003 | 烟雾传感器 | C楼走廊 |

## 2 FR-01 查看设备信息

**角色**：报修人、维修人员

**前置条件**：设备清单已加载；用户已进入设备查询入口。

**输入**：设备编号 `deviceId`（从清单中选择，或手工输入编号）。

**正常结果**：显示该设备的编号、名称、位置三项信息，例如输入 `DEV-002`，显示"智能门锁 / B202实验室"。查询为只读操作，不修改清单内容。

**异常结果**：

1. 输入清单中不存在的编号（如 `DEV-999`）：提示"设备不存在"，不显示空白记录，也不创建任何新数据。
2. 编号为空或只含空格：提示"请输入设备编号"，不执行查询。

**验收条件**（逐条可检查）：

- [ ] 用 `DEV-002` 查询，输出同时包含 `智能门锁` 与 `B202实验室`。
- [ ] 用 `DEV-999` 查询，出现"设备不存在"提示，且不输出任何设备字段。
- [ ] 输入空字符串或 `"   "` 时出现提示，且无查询结果输出。
- [ ] 查询前后 `data/devices.csv` 的内容逐字节不变。

## 3 FR-02 提交报修

**角色**：报修人

**前置条件**：目标设备已存在于清单中（通常先经过 FR-01 查到该设备）；用户处于报修提交入口。

**输入**：

- 设备编号 `deviceId`，必须是清单内设备；
- 故障描述 `description`，去除首尾空格后长度大于 0。

**正常结果**：生成一张工单，包含 `orderId`（系统生成，本实验用 `WO-` 加四位序号，如 `WO-0001`）、`deviceId`、`description`、`status`，其中 `status` 固定为 `PENDING`。界面给出"报修已提交，工单号 WO-0001"一类确认信息。

**异常结果**：

1. 故障描述为空或只含空格：提示"请填写故障描述"，**不创建工单**。
2. 设备编号不在清单内：提示"设备不存在"，**不创建工单**。
3. 设备编号与故障描述同时缺失：分别给出上述两条提示，仍**不创建工单**。

**验收条件**：

- [ ] 正常提交后能查到该工单，且 `status` 值为 `PENDING`。
- [ ] 只输入空格作为故障描述时，工单总数不变。
- [ ] 使用 `DEV-999` 提交时，工单总数不变。
- [ ] 连续提交两次，得到两个不同的 `orderId`，两张工单互不覆盖。
- [ ] 提交成功后生成的工单能按 `deviceId` 关联回 FR-01 中的设备。

## 4 FR-03 更新工单状态

**角色**：维修人员

**前置条件**：工单已存在（由 FR-02 创建），当前状态为三个固定值之一。

**输入**：工单号 `orderId`、目标状态 `target`（`PROCESSING` 或 `COMPLETED`）。

**业务规则**：只允许两条转换，创建时初始状态为 `PENDING`。

| 当前状态 \ 目标状态 | PENDING | PROCESSING | COMPLETED |
| --- | --- | --- | --- |
| **PENDING** | 拒绝（状态不变） | **允许**（开始维修） | 拒绝（禁止跳级） |
| **PROCESSING** | 拒绝（禁止回退） | 拒绝（相同状态） | **允许**（完成维修） |
| **COMPLETED** | 拒绝（禁止回退） | 拒绝（终态不再流转） | 拒绝（相同状态） |

**正常结果**：

- 当前 `PENDING`、目标 `PROCESSING`：允许，状态更新为 `PROCESSING`。
- 当前 `PROCESSING`、目标 `COMPLETED`：允许，状态更新为 `COMPLETED`。

**异常结果**：上表其余 7 种组合一律拒绝，工单状态保持原值不变，并提示"不允许的状态转换"。重点两类：

1. 跳级：`PENDING` 直接到 `COMPLETED` 必须拒绝，未开始维修就不能算完成；
2. 回退与重复：`COMPLETED` 转回 `PROCESSING`、`PROCESSING` 转回 `PENDING`、以及任何"当前状态等于目标状态"的请求，全部拒绝。

**验收条件**：

- [ ] 固定 4 项测试结果与预期一致：T01 `PENDING→PROCESSING` 为 true，T02 `PROCESSING→COMPLETED` 为 true，T03 `PENDING→COMPLETED` 为 false，T04 `COMPLETED→PROCESSING` 为 false。
- [ ] 被拒绝时工单的 `status` 字段前后一致。
- [ ] 判断函数只看"当前状态"和"目标状态"两个入参，不读写文件、不查数据库、不联网。
- [ ] 函数对不在三个固定值内的输入（如 `"DONE"`、空值）返回拒绝，不抛未处理异常。

## 5 需求与模型、代码的对应关系

| 需求 | 用例图中的用例 | 相关模型 | 相关代码 |
| --- | --- | --- | --- |
| FR-01 查看设备信息 | UC-01 查看设备信息 | 类图 `Device`（deviceId、name、location） | 不实现 |
| FR-02 提交报修 | UC-02 提交报修 | 类图 `WorkOrder`（初始 `status=PENDING`） | 不实现 |

状态规则在两处必须一致：本文件第 4 节表格、状态图中的两条转换、`StatusRule.java` 中的判断。三者不一致时以本条业务规则为准，由 B 和 C 分别修正各自的文件。

## 6 本次实验不实现的内容

- 登录、权限校验、多用户账号体系；
- 数据库与持久化，工单只存在于内存中；
- 网页界面、接口服务；
- MQTT 或任何真实设备通信，设备数据只来自 `data/devices.csv`；
- 历史记录、撤销、重新打开工单等扩展状态。
